# 报告撰写规范

写报告时按下面的骨架组织内容，**先想清楚读者是谁**（给领导看 vs 给工程师看，深度和术语完全不同）。

## 标准骨架

```markdown
# <标题：一句话说清这是什么>

## 摘要
3-5 句话讲清：做了什么、结果如何、结论是什么。**读者只读这一段也该够用**。

## 背景与目标
为什么要做这件事？解决什么问题？成功的标准是什么？

## 做法
分点说明关键步骤。每点先说结论再说细节——**先给判断，再给论证**。

## 结果
- 有数据给数据（数字、对比、趋势）
- 没有数据就明确说「未做量化验证」，不要含糊

## 结论与后续
- 结论：能落地的判断，不是「还需要进一步研究」
- 后续：具体动作 + 负责人 + 时间点（没有就写「无」）

## 附录
原始数据、详细表格、参考链接
```

## 硬性要求

1. **结论先行**：每个小节的第一句就是结论，不要把结论藏在段落末尾
2. **数据说话**：涉及效果/性能/质量的断言，尽量给数字。给不出就说清楚没有量化
3. **不编造**：没有的数据、没做过的测试、没验证的结论——一律不写。宁可写「待验证」也不要虚构
4. **可执行**：后续建议必须是具体动作（「把 X 改成 Y」「补 Z 的测试」），不是「加强 X」「优化 Y」
5. **中文标点**：正文用中文全角标点（，。：；），代码/路径/命令用半角
6. **不要罗列流水账**：按重要性排序，不是按时间顺序

## 交付前自查

- 复杂工程先 task_status 查看已持久保存的计划，按当前小任务执行；若要求细化，先 set_plan，不要一边全量遍历一边反复声称准备写文档。
- 所有提取清单、转换脚本、分析笔记和分节草稿放到工作区 `.agent/tasks/<任务编号>/`；不要在源码根目录散落临时文件。
- 每个模块分别写分析笔记，至少说明职责、主要接口及输入输出（含单位/取值约束）、核心数据结构、调用与数据流、分支与边界异常、源码路径及位置。不能用全局概述替代逐模块说明；未知参数和未验证行为明确标记，不得为了凑字数推测实现。
- 当前小任务的笔记写完后用 update_task 提交验收，失败就补充证据或修改该笔记；通过后继续下一项。不要把“读取成功”当成模块分析完成。
- 有 assemble_document 工具时，所有分析小任务完成后再汇总笔记；随后 read_file 检查最终 DOCX，核对模块覆盖、接口和未核实项，再完成验证步骤。结构校验和字数下限只是基本检查，不能替代内容核实。

- 用户要求 Word/.docx 时，调用 write_file，path 使用 .docx，content 提供完整正文。工具会生成真实 Word 包并校验结构；不要将纯文本改后缀，不要 append_file 追加 DOCX。
- 生成后必须 read_file 重新读取，确认格式校验通过且正文完整；“文件写入成功”不代表报告写完。只有标题、占位文字或断句的文件不能交付。
