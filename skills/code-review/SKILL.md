# 代码审查规范

审查代码时按以下维度逐项检查，**不要泛泛而谈**——每条意见都要指向具体代码行和具体问题。

## 审查维度

### 1. 正确性
- 逻辑分支是否覆盖所有情况？边界条件（空列表、空字符串、0、None）处理了吗？
- 是否有「看起来对但实际错」的表达式（运算符优先级、浮点比较、`is` vs `==`）
- 循环里有没有漏掉最后一个元素？`range(len(x)-1)` 这类 off-by-one

### 2. 异常处理
- 是否有裸 `except:` 或 `except Exception: pass`（吞掉错误等于没有错误处理）
- 资源是否正确释放（文件、锁、连接）？用 `with` / `try-finally`
- 失败时给用户的报错信息是否可操作（说清「怎么修」，不只是「出错了」）

### 3. 安全
- **注入风险**：SQL 拼接、命令拼接、路径拼接 → 必须参数化 / 白名单
- **越权**：文件操作是否限制在允许的目录内？路径是否可能被 `../` 穿越？
- **硬编码密钥**：源码里的 API Key / 密码 / Token 一律标为严重问题
- **反序列化 / 动态执行**：`eval`、`exec`、`pickle` 加载不可信数据

### 4. 可维护性
- 命名是否表达意图（不是 `a`、`tmp`、`data2`）？
- 函数是否过长、职责是否过多？超过 50 行就该拆
- 有无重复逻辑可以提取？
- 注释解释「为什么」，而不是复述「做了什么」（后者交给命名）

### 5. 性能
- 循环里有没有可以提前退出/批量化的？
- 嵌套循环导致的 O(n²)？在循环里反复调用同一个昂贵函数？

## 输出格式

```
【严重】文件:行号 —— 问题描述 → 建议改法
【一般】...
【提示】...
```

- 每条**必须**带文件名和行号；定位不到就说明「无法定位到具体行」
- 「严重」只给真正会导致错误/数据损坏/安全问题的问题，不要滥用
- 每条都要给**具体改法**（贴出改后的代码片段），不要只说「建议优化」

## 注意事项

- 先读懂代码在做什么，再判断质量——不要因为风格偏好就报问题
- 如果代码有测试，一并检查测试是否覆盖了关键路径
- 没问题就直说「未发现问题」，不要凑数
